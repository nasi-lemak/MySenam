# HTTP routes (reference)

A reference to every one of the application's own HTTP routes: each is a `route.ts` under `src/app/api/`, and `tests/docs.test.ts` checks that every route listed here exists, that every route is listed, and that each method listed is one the route answers and each it answers is listed. The description of each is the doc comment on its handler; the code is the final word on fields. The public, key-authenticated API for venues' own systems is in [external API](../integrations/external-api.md).

**Times.** A time of day is minutes from the business day's midnight
(`1087` is 18:07; past `1440` is after midnight) or `"HH:MM"`. A booking's
time is `start` and `end`, or `start` and `minutes`; the older `hours`, a list
of the board's column starts in hours (`[18, 19]`), is still read
(`readTime` in `src/lib/api.ts`). Where a route took `startHour`/`endHour` or
`fromHour`/`untilHour`, it takes `start`/`end` or `fromMin`/`untilMin` and
still reads the older names.

## How every route behaves

These hold for every route below unless its row says otherwise.

- **Who is asking.** A customer is signed in by the `ms_session` cookie
  (`/api/auth/*`, Google at `/api/auth/google`); staff by `ms_admin`
  (`/api/admin/auth/*`). A booking made without an account is reached with
  its code and the phone number it was made with, never the code alone. A
  coach and a tournament official have a private link of their own instead of
  an account (`/api/coach/:token/*`, `/api/officials/:token`), which decides
  no approval: a coach reviews applications signed in to their own account
  (`/api/my/reviews`); a venue's own
  systems use an API key ([external API](../integrations/external-api.md)).
- **What staff may do.** Every admin route checks the session (`401` without
  one), then the role: the front desk is refused what only a manager does
  (`403`, code `MANAGER_ONLY`; the list is `MANAGER_ONLY` in
  `src/lib/roles.ts`), and anything about a venue its staff do not run is
  refused (`403`); branch staff see their venue, business managers their
  branches, platform owners everything
  ([tenancy](tenancy.md)). Where the install requires two-factor sign-in, an
  account without it is refused everything but setting it up (`403`, code
  `TWO_FACTOR_REQUIRED`), and is not staff to the public routes that
  recognise staff either
  ([two-factor sign-in](authentication.md#two-factor-sign-in)).
- **Bodies.** A JSON body must be an object: anything else is `400`. A name
  a booking, class place, waiting list or account keeps is at most 100
  characters (`400` `NAME_TOO_LONG`), an email at most 254
  ([security](security.md#what-a-request-may-send)).
- **Requests from another site.** A request that changes something and
  carries a session cookie must come from the app's own pages: one whose
  `Origin` (or `Sec-Fetch-Site`) says another site is refused (`403`) before
  it reaches the route ([security](security.md#requests-from-another-site)).
- **Answers** are JSON. A refusal is `{ error, code?, vars? }`: `error` in
  English for logs and staff, `code` a stable name the customer pages
  translate (the `err.*` phrases in `src/lib/i18n.ts`), `vars` what the
  message quotes. A name quoted by its key as well (`nameKey`, such as
  `pre.con.student` for a built-in concession) is said in the reader's
  language; `name` is its English.

  | Status | Means |
  | ------ | ----- |
  | `400` | The request is malformed: a field missing or of the wrong kind |
  | `401` | Sign in first |
  | `403` | Signed in, but not allowed (role, venue, another site, phone not checked) |
  | `404` | Not found, or not yours to see: a private game, another customer's booking |
  | `409` | Refused by a rule of the business: the time is taken, past the cutoff, the game is full |
  | `429` | Too many requests; `Retry-After` says when to try again ([security](security.md#rate-limiting)) |
  | `503` | Busy (`code: "BUSY"`, `Retry-After: 2`): nothing was kept, so sending it again is safe |

  The app's own pages and the staff dashboard read every answer through one
  function, `readJson` (`src/lib/read-response.ts`): an answer that is not
  the app's (the proxy's HTML page while the app restarts, a 5xx with no
  `error` of the app's own, no body) becomes the refusal `SITE_BUSY` (*the
  site did not answer properly: wait a moment and try again, and check
  whether it went through before doing it twice*), said in the reader's
  language, never a JSON parser's error; a success status without JSON
  throws that sentence. `tests/read-response.test.ts` fails on a client file
  that calls `Response.json()` itself.
- **Text the server words for staff screens** (a warning, a reason, a list
  of changes, a summary) comes in English and, beside it, as a phrase with
  its values: a field named for it with `Phrase` or `Phrases` (`warnings` and
  `phrases`, `unusableReason` and `unusablePhrase`, `changes` and
  `changePhrases`), `{ key, vars }` where `key` is an `srv.` phrase of the
  staff dictionaries and a value may itself be one. The dashboard says it in
  the staff language; what people typed and providers' errors stay values
  ([regions and languages](../product/regions-and-tax.md)).
- **Money.** No route marks anything paid because it was called: payment
  routes answer with the gateway's page to send the payer to, and only the
  gateway's signed report or the redirect's check marks it paid
  ([payments and credit](../features/payments-and-credit.md)).

## The main workflows, by route

Where to start for each, in the order a client calls them. The rows below
have the fields.

- **Booking a court:** `GET /api/availability` (starts and prices) →
  `GET /api/quote` → `POST /api/bookings` (answers `booking`, `holdUntil` if
  it must be paid online to be kept) → `POST /api/payments` (the page to pay
  on) → `GET /api/bookings?code&phone`. Changing it:
  `GET`/`POST /api/bookings/reschedule`; cancelling:
  `POST /api/bookings/cancel`. Staff: `/api/admin/bookings*`.
- **Payments and refunds:** `POST /api/payments` and the provider's report to
  `/api/payments/:provider/callback`; refunds owed and made are on the
  booking (`refunds`), and staff's under `/api/admin/online-payments`.
- **Open games and matchmaking:** `GET /api/games` and
  `GET /api/games/recommended` (suggested, with reasons) →
  `POST /api/games/:id` (`join`, `leave`, `pay`, `invite`, `keepPlace`) →
  the host's `POST /api/games/:id/players/:playerId`,
  `GET /api/games/:id/candidates` and `GET`/`POST /api/games/:id/move`.
- **Tournaments:** staff `POST /api/admin/tournaments` →
  `POST /api/admin/tournaments/:id` (`draw`) → results at
  `/api/admin/tournaments/:id/matches/:matchId`; players
  `POST /api/tournaments/:id` (`enter`, `report`, `confirm`, `dispute`);
  officials `/api/officials/:token`; on the day the *Now and next* board at
  `/api/admin/tournaments/:id/day` and the public `GET /api/tournaments/:id/live`.
- **Running a venue:** `/api/admin/venues`, `/api/admin/courts`,
  `/api/admin/peak-rules`, `/api/admin/booking-policies`,
  `/api/admin/venues/:id/payment-settings`, and `/api/admin/go-live` to ask
  to go live.

### Hours and rates from a date

[hours from a date](../features/booking.md#hours-from-a-date),

### MCP server for AI assistants (no credentials, a venue's key, or a member of staff signed in; see [MCP server](../integrations/mcp.md))

| Method | Path | Description |
| ------ | ---- | ----------- |
| POST | `/api/mcp` | One JSON-RPC 2.0 message of the Model Context Protocol (Streamable HTTP, stateless, answered with JSON; a notification `202`): `initialize`, `ping`, `tools/list`, `tools/call`. No `Authorization`: the public tools (60 a minute per address); `Bearer <key>`: also the key's venue's tools up to its scope (120 a minute per key); a bad key `401` with `WWW-Authenticate`, never anonymous. A cookie never authenticates; an `Origin` not the site's is `403`; an unsupported `MCP-Protocol-Version` `400` |
| GET/DELETE | `/api/mcp` | `405` (`Allow: POST`): no event stream and no session |
| POST | `/api/mcp/staff` | The same protocol for a member of staff signed in from an assistant's connector ([signing in](../integrations/mcp.md#signing-in-from-an-ai-assistant)): `Bearer <access token>` for this address only; without a good one `401` with `WWW-Authenticate: Bearer resource_metadata="<site>/.well-known/oauth-protected-resource/api/mcp/staff"`. The tools the grant's scopes and the person's current role reach, for the one venue allowed, including the [configuration tools](../integrations/mcp.md#changing-the-venues-settings) (preview, then `confirm` with the `previewToken`). 120 a minute per connection; no cookie read; a foreign `Origin` `403` |
| GET/DELETE | `/api/mcp/staff` | `405` (`Allow: POST`) |
| POST | `/api/oauth/register` | RFC 7591: `{ redirect_uris, client_name?, client_uri?, grant_types?, response_types?, token_endpoint_auth_method? }` → `201 { client_id, … , token_endpoint_auth_method: "none" }`, never a secret; redirect URIs `https` or loopback `http`; `400 invalid_redirect_uri` / `invalid_client_metadata`; 30 an hour per address |
| GET | `/api/oauth/authorize` | The authorization request's own query (for the consent page `/oauth/authorize`, with the staff session cookie) → `400 { problem: "client" \| "redirect" }` (never sent anywhere), `{ redirect }` (an OAuth error back to the registered address with `state`), `{ signIn }` (the staff sign-in, coming back; also while two-factor sign-in is still to set up), or `{ request, person, venues }` (the client's unverified name, the return host, the scopes, and each venue with the person's role and what it may allow) |
| POST | `/api/oauth/authorize` | `{ query, decision: "allow" \| "deny", venueId, scopes }` as JSON from this site (otherwise `403`), signed in as staff (`401`) → `{ redirect }` with the code and `state`, or `access_denied`; `403` for a venue not managed or a scope the role may not allow (front desk: `venue:configure`), `400` for one not asked for. Logged (`oauth.granted`) |
| POST | `/api/oauth/token` | Form-encoded: `grant_type=authorization_code` (`code`, `redirect_uri`, `client_id`, `code_verifier`, `resource?`) or `refresh_token` (`refresh_token`, `client_id`, `scope?`, `resource?`) → `{ access_token, token_type: "Bearer", expires_in: 3600, refresh_token, scope }`; OAuth errors (`invalid_grant`, `invalid_target`, `invalid_scope`, `unsupported_grant_type`) as `400`. A code or refresh token used twice ends the connection. 600 in 10 minutes per address |
| POST | `/api/oauth/revoke` | RFC 7009, form-encoded `token`, `client_id`: the connection it belongs to ends; always `200` |

The discovery documents are outside `/api`: `GET /.well-known/oauth-protected-resource`
and `GET /.well-known/oauth-protected-resource/api/mcp/staff` (RFC 9728), and
`GET /.well-known/oauth-authorization-server` (RFC 8414), each public and
readable from any site.

### Public API for venues' own systems (key; see [external API](../integrations/external-api.md))

| Method | Path | Description |
| ------ | ---- | ----------- |
| GET | `/api/v1/availability` | `?date=YYYY-MM-DD[&sport=]` → each court's day: `starts` (minute, longest length), `policy`, and `slots` in columns of `grid` minutes with price, free or `partly` (or `unsupervised`, where the activity needs somebody qualified on duty and nobody is rostered). `unit` is `grid` in hours, what a booking's `hours` are starts of |
| GET | `/api/v1/bookings` | `?from=&to=` (at most 31 days) → the venue's bookings, cancelled ones included |
| POST | `/api/v1/bookings` | `{ courtId, date, start, end \| minutes, name, phone, email?, players?, participantIds?, customerTakesPart?, concessionId?, placeConcessions?, promoCode?, guestOf?, expectedTotal? }` (or `hours: [9, 10]` in the court's `unit`) → a booking, as the venue's own system makes it (write keys), held to the venue's policies as every path is ([the same policies on every path](../features/booking.md#the-same-policies-on-every-path)), 409 with the booking form's codes and words for a system: the venue open, who may book a members-only or private venue (the number, or each person named where only they take places: `R9_NOT_MEMBER`, `R9_NOT_LISTED`, `ENT_MEMBERS_PLACE`), the house rules (`LIMIT_*`), the limit on online bookings without an account (`GUEST_SURGE`, which bookings through a key count towards), a blocked number (`PHONE_BLOCKED`), with `guestOf` (the host's number) a member's or resident's guest counted against the host's guest allowance as at the counter (`GC8_*`, never overridden; [members' and residents' guests](../features/booking.md#members-and-residents-guests-at-the-counter-and-through-the-api)), no-show strikes (`STRIKES_COUNTER`: a key takes no money, so what online is held until paid is refused here), the unpaid-bookings limit (`PHONE_LIMIT_*`), and the customer's own agreement to the venue's waiver already on record (`WAIVER_NEEDED`). A key never overrides: `overridePolicies`, `overrideReason`, `paidAtCounter` or `override` are refused (`R9_API_NO_OVERRIDE`, 400). The customer is sent the usual confirmation. Unpaid; the venue settles it as any other. `participantIds`: participants the venue knows with a live guardian on `phone` and the guardian's waiver agreement on record ([external API](../integrations/external-api.md)); the booking carries `participants`. Discounts as the booking form and the counter take them ([discounts together](../features/pricing.md#discounts-together)): `concessionId` (the booking's concession, on the venue's word), `placeConcessions` (`[{ participantId, concessionId }]`, `null` for the customer's own place), `promoCode`; best-effort, the response carrying `discount`, `promoError`, `promoErrorCode` and `concessionError` beside `booking`; `expectedTotal` (whole cents, the price the system was quoted, `400` otherwise) refuses with 409 `PRICE_CHANGED` and keeps nothing where the booking now costs another price (`vars.amount`, `vars.cents`) |
| GET | `/api/v1/bookings/:code` | One of the venue's bookings, by its code, with `participants` |
| POST | `/api/v1/bookings/:code/cancel` | Cancel one of the venue's bookings, as its staff would (write keys). The customer is told. In the staff activity log (`booking.cancelled`) under the key's name, as `POST /api/v1/bookings` is (`booking.created`) |
| GET | `/api/v1/bookings/:code/withdraw` | → `options`: who is on one of the venue's bookings and whether each can be taken off now, with what it would do, as the counter sees it (`GET /api/admin/bookings/withdraw`; fields as `GET /api/bookings/withdraw`) |
| POST | `/api/v1/bookings/:code/withdraw` | `{ placeId \| participantId \| customer: true \| unnamed: n, reason? }` (write keys) → take them off as the counter does ([taking one person off a booking](../features/booking.md#taking-one-person-off-a-booking)): the counter's terms (up to the end of the booking, in full), the same refusals (`ENT_WITHDRAW_*`, `KIT_STILL_OUT`, `CANCEL_PLAYED`, 409), the same money (online money back now), the customer told by email; `booking`, `withdrawal`, `refunds`. In the activity log (`booking.place_withdrawn`) under the key. Another venue's booking is 404. An optional `Idempotency-Key` header (1–255 printable characters): the same key again answers with the withdrawal it made (`replayed: true`) and takes nobody else off; used for a different request, 422 |
| GET | `/api/v1/venue` | The key's venue: its details, hours and courts with their rates (and `entry` on a court taking entries with no set time; read only) |
| GET | `/api/v1/waitlist` | `?date=YYYY-MM-DD` → the venue's waiting lists that day, each entry with `madeBy`; never an offer's token |
| POST | `/api/v1/waitlist` | `{ classId \| courtId, date, start, end, name, phone, email?, participantIds?, customerTakesPart?, confirmWho?, locale? }` → queue somebody as the venue's counter does (write keys); participants as for `POST /api/v1/bookings` ([external API](../integrations/external-api.md)); an override field or `paidAtCounter` is refused (`R9_API_NO_OVERRIDE`, 400) |
| DELETE | `/api/v1/waitlist` | `{ entryId }` → take off an entry the venue made (write keys); a customer's own online entry is refused (409) |

Prices are always computed server-side; the client's displayed total is informational.
